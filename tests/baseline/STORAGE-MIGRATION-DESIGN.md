# Storage migration design (proposal)

Recorded 2026-09-29. This is the complete design for review, not an implementation or approval to remove the existing database. Keep the old source/API and frozen PostgreSQL baseline available until the replacement passes its contract tests. The objective is to stop storing the large chain tables and remove PostgreSQL and the current Syncer from the **production runtime**, while retaining the required API behavior.

## Scope and target architecture

| API | Target data source | Compatibility decision |
| --- | --- | --- |
| `POST /Wallet/records` | Chia full-node RPC; on-demand coin classification and analysis via the existing coin processor | Keep `coinType`, `includeAnalysis`, hint, pagination, ordering, balance, and response shape. Make the already-present height bounds effective. |
| `POST /Wallet/get-puzzle` | Chia coin record plus puzzle-and-solution RPC | Keep response/error shape; add optional confirmation-height bounds. |
| `POST /Wallet/get-coin-solution` | Chia coin record plus puzzle-and-solution RPC | Keep both legacy `coinId` and array `coinIds` response shapes; add optional confirmation-height bounds. |
| `POST /Wallet/get-block` | Chia block RPC | Keep `blocks`/`refBlocks` and generator gzip/Base64 representation. |
| `GET /Misc/prices` | Tiny local SQLite latest-price cache, refreshed from the configured external source | Reply with the last stored snapshot immediately; refresh in background. Keep JSON fields and ordering. |
| `POST /Wallet/pushtx` | Chia RPC; local log file | Remove PostgreSQL push log dependency without changing the transaction response. |
| `POST /Wallet/offers`, `GET /Wallet/network`, `GET /Misc/taildb`, `GET /Misc/version` | Existing external service/config/file/assembly | Business behavior unchanged; remove incidental PostgreSQL constructor dependency. |

All `/Name/*`, all `/Inscription/*`, and `POST /Wallet/analysis` are planned for removal. Their old snapshots are historical, not migration gates. `/Wallet/offers` and `/Wallet/network` are otherwise outside this migration. No new complete-chain historical parity exercise is required; use the existing real-data baseline and targeted cases to verify the relevant contracts.

The API talks directly to the existing local Chia full node and coin processor. It uses one small, persistent SQLite file for **both the latest prices and mandatory coin-classification/analysis cache**. SQLite is part of the target design, not a contingency for poor performance. It does **not** copy raw block, coin, hint, puzzle, or solution history into SQLite. The existing Syncer is not deployed after cutover. Keep its source in the old repository unless a separate cleanup is wanted. PostgreSQL is removed from the production Compose, API dependency injection, package references, and configuration only after the retained routes no longer open it. The frozen baseline test environment may continue using PostgreSQL.

## Coin and block API behavior

For `records`, fetch by puzzle hash or hint through Chia RPC. `coinType` takes precedence over `hint`, as today. For class filtering, retrieve candidate hinted child coins, fetch each parent coin's spend, and pass its puzzle/solution and metadata to the existing coin processor **only on a cache miss**. Match its module identifier to `CatV2`, `DidV1`, or `NftV1`; include its `analysis` JSON only when requested. Filter before ordering and pagination. Preserve the current empty/missing result behavior, per-hash grouping, `peekHeight`, and all-history balance semantics. Class-filtered `balance` and `balanceInfo` remain absent/null as currently. Bound RPC fan-out.

The SQLite classification cache stores the minimal derived result keyed by parent coin ID and the relevant chain/spend identity: class/module identifier, analysis JSON, computed status, and enough height/block identity to invalidate it after a reorg. Compute and persist both class and analysis together, even when the first request has `includeAnalysis: false`, so a later analysis request does not repeat the same parsing. Cache confirmed negative classifications too, to avoid repeatedly parsing non-CAT/DID/NFT spends. Do not treat transient RPC/processor errors as negative results. Coalesce concurrent misses for the same key within an instance; a successful lookup writes atomically, then subsequent requests reuse it after process restart. On a reorg or changed spend identity, invalidate/recompute affected entries. Set a size/retention policy based on measured use, but eviction must never alter API semantics: it only causes recomputation. This is a **cache**, not a historical full-chain index or replacement Syncer.

Height filtering is by **coin confirmation height**: `startHeight` inclusive, `endHeight` exclusive. Omitted bounds preserve the old no-filter request. `records` currently accepts these fields but ignores them; making them effective is the agreed intentional change. Add optional fields with the same names to `get-puzzle` and `get-coin-solution`. Fetch each matching coin's puzzle and solution using its actual spent height, not the caller's confirmation-height bound. Do not reinterpret the height range as a spend-height range or make `records` balance into a range total. Define and test invalid/reversed bounds before implementation; otherwise preserve the existing validation and error shapes.

For `get-block`, retrieve requested heights and reference heights from Chia, deduplicate references as the old SQL does, and preserve the old ordering, unknown-height and duplicate-height behavior. Map each block to `{index,generator,generator_ref_list}` under the existing `blocks`/`refBlocks` response. Apply the same gzip to generator bytes so JSON still carries Base64-encoded compressed bytes. Do not expose raw Chia RPC JSON.

## Existing baseline and remaining focused cases

The frozen old API/PostgreSQL baseline is intentionally a limited mainnet slice, not a complete chain mirror. Its Syncer is stopped; it has 239,000 blocks, 15,200,006 coin records, 15,000,003 hints, and 6,642 parsed class rows. The 28 C# xUnit tests include spent/unspent records and pagination; real nonempty puzzle/solution; block generator and edge cases; and positive `CatV2`, `DidV1`, `NftV1` records with selected `analysis` fields from narrowly seeded public-mainnet samples near height 9,000,000. The bounded C# scanner found those samples within 700 blocks; no 100,000-block sync or full-chain comparison is required. `peekHeight` and balances in snapshots describe this frozen slice, not complete mainnet state. The runner and exact fixture rules are documented in [README.md](README.md).

Before migration, add targeted baseline cases for positive ordinary hint lookup, multiple puzzle hashes and coin IDs, unspent solution behavior, and any paging/ordering edge still used by retained routes. The existing ignored-height snapshot describes old behavior only; new height-bound tests assert the agreed contract. Class cases already cover the three required types, so do not duplicate them with a broad sync. The online prices fixture below supplies a positive price baseline; the frozen test database has no price rows. Do not create new migration gates for removed Name, Inscription, or wallet-analysis endpoints.

The old `get-puzzle`/`get-coin-solution` snapshots initially showed empty reveal/solution because the limited test database had no parsed class rows, not because spent on-chain coins lack reveals. A one-off analysis-only parse populated the narrow test slice, and a real nonempty reveal/solution case now verifies both endpoints. This distinction matters when comparing old snapshots to Chia RPC.

## Prices: production baseline and refresh

`GET https://walletapi.chiabee.net/misc/prices` returned HTTP 200 at `2026-09-29 06:57:57 UTC`. Its exact JSON body is saved in [production-prices-2026-09-29.json](production-prices-2026-09-29.json): three `coinbase` records for XCH→CNY, XCH→USD, and XCH→USDT, ordered by `to`. The timestamps are part of the response; notably USDT is from 2023 while the other two are from 2025. The baseline therefore tests the payload shape, currency coverage, ordering, decimal precision, and independent per-currency last-known values; it must not assume all rows are fresh or have one shared update time. Live prices are time-varying, so exact numeric equality applies to this captured fixture, not to later live requests.

SQLite stores the last successful value per `from,to` (including `source`, decimal `price`, and original `time`) plus refresh metadata. On each request: read and return the stored snapshot immediately; if a refresh is eligible, start it without making the caller wait. At most **one external price query/update per API instance** may run at a time. An in-process single-flight gate is sufficient; no cross-instance distributed lock is required. Use a configurable minimum refresh interval, a hard HTTP timeout, failure backoff with a cap, and a cooldown recorded independently of request volume, so repeated requests cannot cause a bounce or DoS. A successful query validates all returned rows and atomically upserts only valid currency values; a failed, empty, or partial response cannot wipe previously known currencies. Do not overwrite a newer currency value with an older timestamp. Log refresh failures and keep serving stale values. SQLite transactions/WAL protect readers from partial writes.

Cold start needs an explicit last-known seed/import before production cutover so the first response is not unexpectedly `[]`. The captured production fixture is a permissible initial seed, but its old timestamps should be visible as-is, not labeled current market prices. Preserve the configured price source or select an equivalent source that actually supplies all retained currencies; the legacy Syncer Coinbase job lists USD and CNY only, whereas the production API also returns historical USDT. Decide the concrete upstream adapter during implementation by inspecting production configuration and confirming it can refresh USD/CNY; USDT may remain a last-known entry until a suitable source exists. Do not fabricate a live USDT price.

## Push log and operational boundaries

Replace `PushLogHelper`'s PostgreSQL write with an append-only, structured local log file in a persistent mounted directory. Keep the same diagnostic fields (time, IP, status, error and transaction/bundle identifier where available); if retaining the full submitted bundle is necessary for operations, keep it in a separately permission-restricted log rather than ordinary application logs. Define rotation/retention and maximum disk usage before deployment. A log write failure is recorded by the application logger and must not change the `pushtx` RPC result, matching the current `finally` behavior. No SQLite table is needed for push logs.

`DataAccess` and `PushLogHelper` currently open PostgreSQL in their constructors, and `WalletController`/`MiscController` inject them even for routes that do not read the database. Split the new RPC/price/log services so `network`, `offers`, `pushtx`, `taildb`, and `version` have no hidden PostgreSQL availability dependency. Remove PostgreSQL-specific exception handling only when all runtime PG paths are gone.

## Implementation and acceptance sequence

1. Preserve the current frozen API/PG test setup and production price fixture. Add the focused xUnit baseline cases listed above; do not broaden into a full chain sync.
2. Introduce Chia-backed coin/block services and the persistent SQLite classification/analysis cache behind the existing controllers. Make the agreed height fields effective. Run the existing 28 xUnit cases and new targeted cases; classify intentional height-field differences separately from regressions. Verify the real CAT/DID/NFT analysis samples, cache hit/miss/restart/reorg behavior, bounded-request RPC counts, and latency.
3. Introduce the local SQLite price cache and per-instance background single-flight refresh. Test cold seed, immediate stale response, simultaneous requests (one outbound query), partial/failing upstream, timeout/backoff, and restart persistence. Use the captured online response as the price contract fixture.
4. Move push logs to a persistent rotated file; decouple incidental PG construction. Test both `pushtx` success/failure response paths and log-write failure isolation without submitting a live transaction in automated tests.
5. Remove the deprecated routes and stop deploying Syncer. After the retained API suite passes against the replacement, remove PostgreSQL from the production deployment and its API references. Keep a rollback deployment/volume snapshot until the cutover is accepted; do not delete production PG data as part of implementation.

The remaining engineering work is to implement and size the mandatory cache and verify the upstream/latency behavior; it is not a decision about whether to use SQLite. The user has confirmed that `coinType` and `includeAnalysis` stay supported, the height contract above is acceptable, prices use the online API baseline, push logs go to files, and one outbound price update per instance is enough.
