# Storage migration design and execution status

Recorded and updated 2026-09-29. This is the single migration design and development status document. The replacement API is implemented on branch `codex/baseline-xunit` and verified in an isolated test-machine container; **production has not been cut over and its PostgreSQL data has not been deleted**. The objective is to stop storing the large chain tables and remove PostgreSQL and the current Syncer from the production runtime while retaining the required API behavior.

## Scope and target architecture

| API | Target data source | Compatibility decision |
| --- | --- | --- |
| `POST /Wallet/records` | Chia full-node RPC; on-demand coin classification and analysis via the existing coin processor | Keep `coinType`, `includeAnalysis`, hint, pagination, ordering, balance, and response shape. Make the already-present height bounds effective. |
| `POST /Wallet/get-puzzle` | Chia coin record plus puzzle-and-solution RPC | Keep response/error shape; add optional confirmation-height bounds. |
| `POST /Wallet/get-coin-solution` | Chia coin record plus puzzle-and-solution RPC | Keep both legacy `coinId` and array `coinIds` response shapes; add optional confirmation-height bounds. |
| `POST /Wallet/get-block` | Chia block RPC | Keep `blocks`/`refBlocks` and generator gzip/Base64 representation. |
| `GET /Misc/prices` | Tiny local SQLite latest-price cache, refreshed from the configured external source | Reply with the last stored snapshot immediately; refresh in background. Keep JSON fields and ordering. |
| `POST /Wallet/pushtx` | Chia RPC; local log file | Remove PostgreSQL push log dependency without changing the transaction response. |
| `POST /Wallet/offers`, `GET /Wallet/network`, `GET /Misc/taildb`, `GET /Misc/version` | Existing external service/config/file/assembly | Business behavior unchanged; remove incidental PostgreSQL constructor dependency. |

All `/Name/*`, all `/Inscription/*`, and `POST /Wallet/analysis` are planned for removal. Their old snapshots are historical, not migration gates. `/Wallet/offers` and `/Wallet/network` are otherwise outside this migration. No new complete-chain historical parity exercise is required; use the existing real-data baseline and targeted cases to verify the relevant contracts.

The API talks directly to the existing local Chia full node and coin processor. It uses one small, persistent SQLite file for **both the latest prices and mandatory coin-classification/analysis cache**. SQLite is part of the target design, not a contingency for poor performance. It does **not** copy raw block, coin, hint, puzzle, or solution history into SQLite. The API code and API-only Docker image no longer reference PostgreSQL; the old Syncer remains in the repository as historical source but is no longer built by the API Dockerfile or started by `deploy.sh`. The frozen baseline test environment continues using PostgreSQL. Its volume must not be deleted during migration.

## Coin and block API behavior

For `records`, fetch by puzzle hash or hint through Chia RPC. `coinType` takes precedence over `hint`, as today. For class filtering, retrieve candidate hinted child coins, fetch each parent coin's spend, and pass its puzzle/solution and metadata to the existing coin processor **only on a cache miss**. Match its module identifier to `CatV2`, `DidV1`, or `NftV1`; include its `analysis` JSON only when requested. Filter before ordering and pagination. Preserve the current empty/missing result behavior, per-hash grouping, `peekHeight`, and all-history balance semantics. Class-filtered `balance` and `balanceInfo` remain absent/null as currently. Bound RPC fan-out.

The SQLite classification cache stores the minimal derived result keyed by parent coin ID and the relevant chain/spend identity: class/module identifier, analysis JSON, spent height, and block hash. Compute and persist both class and analysis together, even when the first request has `includeAnalysis: false`, so a later analysis request does not repeat parsing. Cache confirmed negative classifications too; transient RPC/processor errors are not cached. A bounded set of per-instance keyed locks coalesces concurrent misses. A changed spend height/block hash triggers recomputation after a reorg. The default maximum is 100,000 entries with least-recently-used pruning; eviction changes only computation cost, not API semantics. This is a **cache**, not a historical full-chain index or replacement Syncer.

Height filtering is by **coin confirmation height**: `startHeight` inclusive, `endHeight` exclusive. Omitted bounds preserve the old no-filter request. `records` currently accepts these fields but ignores them; making them effective is the agreed intentional change. Add optional fields with the same names to `get-puzzle` and `get-coin-solution`. Fetch each matching coin's puzzle and solution using its actual spent height, not the caller's confirmation-height bound. Do not reinterpret the height range as a spend-height range or make `records` balance into a range total. Define and test invalid/reversed bounds before implementation; otherwise preserve the existing validation and error shapes.

For `get-block`, retrieve requested heights and reference heights from Chia, deduplicate references as the old SQL does, and preserve the old ordering, unknown-height and duplicate-height behavior. Map each block to `{index,generator,generator_ref_list}` under the existing `blocks`/`refBlocks` response. Apply the same gzip to generator bytes so JSON still carries Base64-encoded compressed bytes. Do not expose raw Chia RPC JSON.

## Existing baseline and remaining focused cases

The frozen old API/PostgreSQL baseline is intentionally a limited mainnet slice, not a complete chain mirror. Its Syncer is stopped; it has 239,000 blocks, 15,200,006 coin records, 15,000,003 hints, and 6,642 parsed class rows. The 31 C# xUnit tests include spent/unspent records, pagination, positive hint and multiple-ID cases; real nonempty puzzle/solution; block generator and edge cases; and positive `CatV2`, `DidV1`, `NftV1` records with selected `analysis` fields from narrowly seeded public-mainnet samples near height 9,000,000. The bounded C# scanner found those samples within 700 blocks; no 100,000-block sync or full-chain comparison is required. `peekHeight` and balances in snapshots describe this frozen slice, not complete mainnet state. The runner and exact fixture rules are documented in [README.md](README.md).

The existing ignored-height snapshot describes old behavior only; new height-bound tests assert the agreed contract. Class cases cover all three required types. The online prices fixture below supplies a positive price baseline; the frozen test database has no price rows. Removed Name, Inscription, and wallet-analysis routes are not migration parity gates.

The old `get-puzzle`/`get-coin-solution` snapshots initially showed empty reveal/solution because the limited test database had no parsed class rows, not because spent on-chain coins lack reveals. A one-off analysis-only parse populated the narrow test slice, and a real nonempty reveal/solution case now verifies both endpoints. This distinction matters when comparing old snapshots to Chia RPC.

## Prices: production baseline and refresh

`GET https://walletapi.chiabee.net/misc/prices` returned HTTP 200 at `2026-09-29 06:57:57 UTC`. Its exact JSON body is saved in [production-prices-2026-09-29.json](production-prices-2026-09-29.json): three `coinbase` records for XCH→CNY, XCH→USD, and XCH→USDT, ordered by `to`. The timestamps are part of the response; notably USDT is from 2023 while the other two are from 2025. The baseline therefore tests the payload shape, currency coverage, ordering, decimal precision, and independent per-currency last-known values; it must not assume all rows are fresh or have one shared update time. Live prices are time-varying, so exact numeric equality applies to this captured fixture, not to later live requests.

SQLite stores the last successful value per `from,to` (including `source`, decimal `price`, and original `time`) plus refresh cooldown/backoff metadata. On each request: read and return the stored snapshot immediately; if a refresh is eligible, start it without making the caller wait. At most **one external price query/update per API instance** may run at a time. The in-process single-flight gate and persisted cooldown prevent request bounce and restart storms; no cross-instance distributed lock is required. The implementation has a configurable minimum interval, 15-second HTTP timeout, and capped failure backoff. Successful rows are atomically upserted; a failed or partial response cannot wipe previously known currencies, and an older timestamp cannot replace a newer value. SQLite WAL protects readers from partial writes.

Cold SQLite is seeded from the captured production fixture, preserving its old timestamps; the API does not label them current market prices. The legacy Coinbase adapter only attempts USD and CNY, while USDT remains an independent historical last-known entry. On the test machine Coinbase, CoinGecko, and CoinPaprika timed out both directly and through the old Syncer proxy on 2026-09-29. CoinGecko/CoinPaprika also need their own response adapters rather than being placed directly in `PriceSourceUrl`, which expects the existing `PriceResponse[]` shape. The user explicitly made obtaining a working live price source a **follow-up task**, not a blocker for the rest of the storage migration. Until configured, `/Misc/prices` serves the captured/stored last values and logs refresh failures; do not present them as live quotes or fabricate USDT updates.

## Push log and operational boundaries

`PushLogHelper`'s PostgreSQL write has been replaced with a structured local JSONL file. It includes time, IP, status, error and the full submitted bundle gzip-compressed/Base64-encoded for legacy diagnostic continuity. On Linux the file is restricted to owner read/write (`0600`); configurable rotation defaults to 10 files × 10 MiB, deleting the oldest rotated file at the cap. Place the log path in the persistent data mount and restrict access to that mount. A log write failure is caught and logged without changing the `pushtx` RPC result. No SQLite table is used for push logs.

The old `DataAccess`, `PushLogHelper`, Name/Inscription cache services, API Npgsql package and PostgreSQL-specific exception handling have been removed from the new API. `network`, `offers`, `pushtx`, `taildb`, and `version` have no hidden PostgreSQL constructor dependency.

## Implementation, verification, and cutover

Completed in the test environment: old API on port 5057 plus PostgreSQL remains frozen; replacement API on isolated port 5058 reads Chia directly and uses a small SQLite file (44 KiB main file plus 89 KiB WAL after the sample tests). The old baseline suite passes **31/31**; the replacement C# xUnit suite in `tests/migration` passes **13/13** including CAT/DID/NFT, height exclusion, puzzle/solution, blocks, prices, single-flight refresh, stale-value preservation on upstream failure, cache persistence, removed routes, and file-log rotation. The API-only Docker image built successfully and passed a separate prices/network smoke test on port 5059. No production process or PG volume was replaced or deleted.

Before production cutover:

1. Configure the API's Chia RPC host/port/certificate path, `CoinProcessorUrl`, a **persistent** mount for `data/prices.sqlite` and `data/pushtx.jsonl`, and, if available, a working price source/proxy. An empty/unreachable price source is allowed only with the explicit stale-price limitation above.
2. Run the migration suite against the candidate deployment. Exercise high-cardinality class requests and observe RPC count/latency and SQLite growth. The cached results are capped at 100,000 entries; a miss or reorg must recompute correctly. The suite does not submit a live transaction or offer; verify `pushtx` response behavior operationally before public cutover.
3. Switch traffic only after retained endpoint verification. Stop the old Syncer deployment and remove PostgreSQL from the **production** Compose/deployment config (the production Compose file is not in this repository). `deploy.sh` no longer starts Syncer, but it does not stop an already-running instance. Preserve the old PG volume and a rollback deployment until accepted; do not delete it as part of cutover.

To run the C# suites on a host with the existing .NET 6 SDK container and both services reachable, set `PAWKET_BASELINE_URL` for `tests/baseline/WalletBackend.BaselineTests.csproj` and `PAWKET_MIGRATION_URL` for `tests/migration/WalletBackend.MigrationTests.csproj`. The old frozen snapshots are not exact live-chain snapshots for the new API: `peekHeight`, balances and newly indexed coins legitimately differ, while the targeted contract assertions remain mandatory.

The remaining work is production configuration/cutover verification and the separately deferred live-price-source task. SQLite caching, the height contract, file push logs, and one outbound price update per instance are implemented decisions, not open architecture choices.
